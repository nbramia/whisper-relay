# ADR-008: Per-tenant backend routing

**Status:** Complete
**Last Updated:** 2026-08-27
**Decision:** Accepted (whisper-relay #40, sibling to #41)

## Context

whisper-relay is built to carry one person's spoken conversations to one LifeOS instance. Every backend client — `HTTPLifeOSClient`, `HTTPAgentBackendClient`, `HTTPHermesBackendClient` — is constructed once at process startup from top-level `Settings` (`LIFEOS_BASE_URL`, `AGENT_BACKEND_URL`, `HERMES_BACKEND_URL`) and reused for the life of the process. `TextBackendRouter.client_for()` resolves a backend *kind* (lifeos/agent/hermes) per request; it has never resolved a *tenant*.

The gateway was widened to also carry a second person's voice turns over a private network, sharing one running process. Because the gateway had no concept of "whose LifeOS is this," every one of her spoken exchanges — her words in, the reply spoken back — was answered by the first person's LifeOS instance and saved into his conversation history instead of hers, including the turn reported at the time as a successful test.

The only remedy available at the time was building and running an entirely separate copy of the service: its own systemd unit, its own environment file kept outside the usual shared-settings location, and its own data directory. That is a heavyweight, error-prone stand-in for ordinary multi-user support, and it doesn't scale past two people sharing a host.

## Decision

Give the gateway a way to know, **per spoken turn**, which person's backend it is talking to — resolved from an operator-issued token, never a client-suppliable field — with a hard failure when that resolution is ambiguous, missing, or unrecognized.

### Two modes, selected by configuration presence

`Settings.tenant_backends: dict[str, TenantBackend]`, parsed from `TENANT_BACKENDS_JSON`, is empty by default.

| Mode | When | Behavior |
|------|------|----------|
| **Single-tenant** | `TENANT_BACKENDS_JSON` unset (default) | Every request uses the one process-wide `TextBackendRouter` built from top-level `Settings`. The tenant-token header is never inspected. This is the *only* mode either running production instance uses today, and it is untouched by this change. |
| **Multi-tenant** | `TENANT_BACKENDS_JSON` has one or more entries | Every voice-turn request must present a token (`X-Whisper-Relay-Tenant-Token` header) matching exactly one configured tenant. A missing or unrecognized token is rejected with `403`; there is no fallback to the process-wide router. |

`TenantBackend` (`config.py`) mirrors the top-level backend settings per tenant — `lifeos_base_url` (required), optional `agent_backend_url` / `hermes_backend_url` (each only "available" for that tenant when its URL is set, mirroring issue #41's no-loopback-default rule — there is no separate per-tenant enabled flag) — plus the required `tenant_token`.

### Why a bearer token, not a free-text tenant id

An early shape considered a plain `X-Tenant-Id` header the client sets to name which tenant it is. That fails closed against config typos but not against a client (or attacker on the same network) simply asserting someone else's id — nothing about a free-text field proves the caller is entitled to claim it.

Instead, the *value itself* must be an operator-issued secret: `tenant_token` is generated by the operator and configured in `TENANT_BACKENDS_JSON`, then given only to that tenant's client. Resolution (`TenantRegistry.resolve`, `tenants.py`) matches the presented header value against every configured token with `hmac.compare_digest`, never a bare dict-hash lookup, so a wrong guess doesn't get to key off timing. Guessing a valid token is a credential-guessing problem, not a spoofing-a-label problem.

Authenticating that the human on the other end of a request really holds the token they present is out of scope here — the token itself is the trust boundary the operator's network already provides (LAN/Tailscale-only exposure). See Scope below.

### Fail closed at every layer

- **Startup:** `build_tenant_registry` raises `TenantConfigError` — a hard crash, not a warning — for a blank `tenant_token` or one reused across two tenants. An ambiguous tenant table must never reach request handling.
- **Per-request:** `routes/voice.py`'s `_resolve_text_backend_router` is called before the audio/transcript body is even read. A missing or unrecognized token raises `HTTPException(403)` immediately; nothing downstream ever sees the request.
- **Cancel:** `POST /api/voice/turn/{id}/cancel` resolves the tenant *first*, the same way as a voice turn — a missing or unrecognized token gets `403` before the turn registry is even touched (issue #48; an earlier version of this ADR described this step as best-effort, which was itself the bug — it let one tenant's token, or none at all, reach another tenant's in-flight turn by id). `TurnRegistry` entries are keyed by tenant, so a resolved-but-wrong tenant also can't reach another tenant's turn — that case gets the same `403` as an unresolved one, not a `404`, so a caller learns nothing about whether the turn_id exists. Only the *upstream* "please stop" call to the tenant's own backend remains best-effort (consistent with [ADR-007](007-explicit-turn-cancellation.md) — cancel never turns a clean local cancel into an error for the caller): the local cancel has already succeeded by that point, so a failure there is a `WARNING` log line, not an error response.

### Additive to backend-kind resolution, not a replacement

`adapters/text_backend.py`'s `TextBackendRouter.client_for()` and `normalize_backend()` are unchanged — they still resolve *which backend* (lifeos/agent/hermes) within whichever tenant's router was already selected. Tenant resolution is a layer above, applied once per request in `routes/voice.py`, then threaded through as an explicit `text_backend` parameter on `TurnPipeline.run_turn` / `run_turn_stream` (default `None` — falls back to the pipeline's own router, i.e. exactly today's single-tenant behavior). All of the existing backend-kind tests pass unmodified, per this issue's acceptance criteria.

## Consequences

- **The two running production instances are unaffected.** Neither sets `TENANT_BACKENDS_JSON`; `TenantRegistry.enabled` is `False` for both, and the tenant-token header is never consulted. They may keep running as fully separate processes indefinitely — this ADR doesn't require migrating them onto one shared process (out of scope, see issue #40).
- **A future shared-process deployment for two or more people** now has a real primitive instead of "run a second copy of the whole service": one process, one `TENANT_BACKENDS_JSON`, per-tenant tokens issued out of band.
- **What this does not cover:** authenticating the human presenting a token (a separate concern — the token is the trust boundary today), per-tenant STT/TTS/storage isolation (turn storage and STT/TTS adapters remain shared across tenants; only the text-backend target is tenant-scoped), and persona-listing accuracy in multi-tenant mode (`app.state.lifeos_personas` is still populated once at startup from the single top-level LifeOS client, not per tenant — a real gap if multi-tenant mode is adopted with different persona sets per tenant, flagged for follow-up rather than solved here).
- A future operator using multi-tenant mode is responsible for generating one high-entropy token per tenant (e.g. `openssl rand -hex 32`) and keeping it out of logs and version control — the same handling as `AGENT_BACKEND_TOKEN`/`HERMES_BACKEND_TOKEN` today.
- **Two instances sharing one checkout should still use distinct `WorkingDirectory=` values**, even though this is orthogonal to `TENANT_BACKENDS_JSON` itself (issue #46). `Settings()` no longer falls back to a `./.env` resolved relative to the CWD by default (see `VOICE_GATEWAY_DOTENV` in `.env.example`), so a shared `WorkingDirectory` is no longer a correctness risk the way it was — but a distinct directory per instance keeps that true by construction rather than by a flag an operator could unset.
